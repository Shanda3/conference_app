# ThunderPlains manual cleanup preparation

This draft prepares an executable production adapter and an organizer-only endpoint at `/api/event-cleanup`. The endpoint returns 404 unless `DEVYO_EVENT_CLEANUP_MODE` is explicitly set to `manual`; no setting is changed by this code. The SQL is a prepared file, not an automatic migration. No event cleanup is scheduled, no contacts have been collected, and no production removal or sending has been performed.

## Permanent scope and preservation

The current deletion engine removes whole Devyo accounts across conferences: private planner JSON, saved sessions, notes and connections; profile/photo/avatar data; shared projections and links; authored messages, memberships and invites; social relationships; push/read/reaction state; and per-owner AI records. Relationships with a deleted peer can disappear from the preserved organizer's views. Independently saved notes/connections belonging to the organizer remain intact and can refer to other people.

New planners contain both public conference programs even before any private use. Conference presence alone is not another conference's private data. The adapter counts actual saved choices, nonempty notes and saved connections separately and includes other-conference choices in the reviewed scope. A published-program mismatch is not automatically a personal edit.

The server-configured protected Clerk user ID must identify the organizer under the pinned production issuer and instance. Display names, moderator roles and guessed email matches are insufficient. Clerk instance ID, production environment and its primary frontend API issuer are checked. Pagination is read twice to detect changing/missing/duplicate IDs. The union includes Clerk-only identities and D1-only owners; equal totals are never considered identity reconciliation. Missing identities and unsupported notifications appear in the review.

D1 schema inspection rejects unknown owner storage. The review binds schema, canonical IDs, conference structure, private-data counts, owner-reference counts and group/relationship policy. Before every target, new identities/data owners, increased private-data counts, new conference structure, new group members/messages/invites, changed schema or unexplained identity disappearance stop execution. Decreases from an already approved operation are allowed. This is account-wide authorization within the reviewed scope caps; it is not a promise to preserve an attendee's later edit to an already reviewed account field.

The organizer and their group/history are never deletion targets. A target-owned group can be removed only when it was explicitly reviewed as empty and all members are also reviewed non-exempt targets. The intent transaction checks this again atomically; a protected/other message or member arriving after review prevents identity deletion. Later pruning again checks that the group is empty, contains no protected/unreviewed member, and belongs to the target whose cleanup completed. Other groups require a new preservation decision. Blindly anonymizing the creator can reactivate a group because its archived state currently derives from the deletion receipt; that approach is not used.

## Recipient handling and the unresolved provider conflict

Recipients are kept only in one invocation's memory. The prepared tables contain no destination field, encrypted recipient, address hash, message body or phone number. No new delivery address can therefore enter D1 backups through this workflow. Each email uses one currently verified address fetched just before approved removal. A newly fetched identity must match the exact canonical target. Addresses are never returned by the endpoint or logged; provider exceptions are replaced with bounded status codes. Each external step has a 30-second deadline, and the local contact reference is released on exit. The notice-attempt deadline is never extended beyond its original 24 hours.

Clerk may already hold contact information before account removal, and existing D1 account data can already contain attendee-authored information. Their preexisting provider retention is distinct from creating a new delivery-contact list. Minimal deletion/confirmation receipts and reviewed scope metadata remain; D1 backups, Clerk logs and independently saved copies have separate retention boundaries requiring explicit acknowledgement. No new attendee backup/export is made.

Cloudflare's Email Sending event analytics include sender, recipient and message information and are retained for **31 days**. Message previews are a separate feature, on by default for new sending domains and retained for about seven days. Disabling previews does not remove recipient analytics. The current permission to erase temporary contact copies after acceptance or within 24 hours does **not** authorize this longer provider retention. This is an unresolved permission conflict, not something a D1 delete or memory-only design can fix. Live execution remains blocked unless amended permission is explicitly recorded and the separate server gate `DEVYO_EVENT_CLEANUP_PROVIDER_RETENTION_APPROVED=email-analytics-31d` is approved and configured. This code sets no such gate.

The requested native sender is `privacy@devyo.app`. An approved restricted `send_email` binding should allow only that sender. Existing Clerk auth mail does not establish arbitrary transactional delivery readiness. No binding, preview setting, quota or DNS is changed by this draft. Numeric quota, domain readiness and previews-off must be independently verified before execution; a proposed binding or `-- / --` quota is insufficient.

Phone-only accounts stay blocked before number capture or deletion, even if a missing-notice recovery waiver exists. There is no SMS sender or automatic substitution of an unverified email. A separate human decision and implementation are required for manual phone confirmations; no current approval is inferred.

## Manual endpoint and deletion ordering

The endpoint requires production mode, the separately applied schema flag, the configured protected organizer's existing authenticated Clerk session, strict recent verification, trusted origin, same-origin mutation checks and an expected-session header. Test hooks are function arguments only and cannot be supplied through HTTP. It accepts exact bounded request shapes; clients cannot choose credentials, provider, issuer, exemption or readiness gates. Responses are private/no-store and never contain recipients.

| Action | Effect |
| --- | --- |
| GET, or POST `preview` | Read the live scope and return hashes, counts, canonical target IDs, blocked notification counts and explicit policy boundaries. No deletion intent. |
| POST `approve` | Require the current hashes, exact permanent-removal phrase, memory/retained-boundary and 31-day-provider acknowledgements; store a contact-free reviewed run for at most 15 minutes. No deletion or sending. |
| POST `execute` | Select one target in that reviewed run, recheck live scope and all delivery/retention gates, then invoke the manual deletion and success-only confirmation flow. No loop or scheduler. |
| POST `renew` | Require a fresh unchanged scope, the same notice policy and exact phrase before renewing the 15-minute action-time approval. |

The normal phrase is `REMOVE REVIEWED DEVYO ACCOUNTS`. A distinct explicitly reviewed recovery policy uses `REMOVE REVIEWED ACCOUNTS WITHOUT GUARANTEED CONFIRMATIONS`. Neither phrase alone is authentication or consent; the server validates the organizer's authenticated action and scope. An earlier publication permission is not action-time removal permission.

After readiness, scope and phone checks, the target gets a contact-free confirmation receipt. The manual intent reuses the existing account-deletion table and closure triggers, revoking public projections and stopping writes. Its `next_attempt_at` is the maximum safe integer so the existing automatic self-service recovery scheduler cannot claim it. Only a new authenticated manual invocation can resume it. Leases/attempt fences prevent conflicting D1 completion.

The adapter derives the Clerk ID from the pinned owner, rechecks instance/issuer, checks current identity existence before any retry, requests deletion, and reconciles authoritative provider absence even after a timeout. Provider absence must be confirmed before the existing transactional `cleanupAccountData` runs. Partial D1 cleanup rolls back and cannot produce success. After guarded empty-group pruning, a fresh check requires actual identity absence, completed D1 receipt and zero active owner references, including group metadata, before allowing an email.

## Interruptions, expiry and uncertain delivery

The durable confirmation claim is metadata-only and permits at most one provider attempt. A receipt in `dispatching`, `accepted` or `uncertain` never becomes sendable again. A timeout, crash after claim, or failure to persist provider acceptance cannot trigger an automatic duplicate. The opaque confirmation header is an investigation aid, not a provider idempotency key. Provider acceptance is not proof of inbox delivery; at-most-one attempt cannot guarantee exactly-once delivery.

A restart after identity removal may lose the only in-memory address. The default result is `contact-lost-after-interruption`; it does not retrieve a contact from backups, logs, files or a durable queue. Finishing removal without that notice requires a new explicit recovery-policy review and phrase. This waiver still cannot remove phone-only targets. A newly approved review can adopt unattempted partial-removal metadata while preserving its receipt and original time limit; it cannot reset a started/accepted/uncertain send. No manual recovery approval has been granted by preparing this code.

If the attempt deadline passes, no email is sent and no address is retained. A recovered operation can report removal without a notice only under the explicit reviewed waiver. No reset/resend endpoint exists. The confirmation describes active account-data removal across conferences, minimal retained receipts, independently saved copies and provider retention; it contains no marketing, tracking, HTML, CC/BCC or unrelated-spam prevention promise.

## Remaining activation decisions and validation

Before any real invocation: reconcile current production identities and the owner; review exact account-wide/private/group/relationship scope; resolve phone-only notices and recovery tradeoffs; obtain amended provider-retention permission; verify the approved restricted sender, previews-off, numeric quota and labeled owner-only test; then obtain exact action-time permanent-removal approval. Schema application, configuration and deployment are separate approval-controlled actions. None is performed by this draft.

Tests use synthetic identities, in-memory SQLite, isolated local D1 and mocked Clerk/email. They cover invalid owner/issuer/instance, identity-only accounts, missing identities, scope increases, owner/group preservation, the message-arrival race, phone blocking, manual lease isolation from scheduled recovery, interrupted transactional cleanup, later restarts, explicit missing-notice recovery, expiry/renewal, wrong notice-policy renewal, uncertain deletion reconciliation, uncertain/blocked duplicate sends, recipient-free persistence, and default-disabled/organizer/origin/session/reverification endpoint gates. Production sender readiness and actual delivery are not established by mocks.
